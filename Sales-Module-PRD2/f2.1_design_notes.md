## 3. Open Questions — análisis y recomendación

### 3.1 OQ2-1: ¿Qué hacer con `self_service` origin en `fn_add_item_from_menu`?

**Contexto:** el enum `order_origin` incluye `self_service`, pero el feature
`SelfServiceView` está stubbeado (sólo muestra "Self service no disponible").
No debería haber órdenes con ese origin en producción, pero el enum existe.

**Opciones del PRD:**
- A) Tratar como `quick`
- B) Lanzar excepción si llega
- C) Comportamiento indefinido

**Recomendación:** **B (fail-loud)** durante PRD 2. El feature no está
implementado; si por algún bug llega un order con `self_service`, queremos
que la transacción falle con error explícito en lugar de silenciosamente
calcular impuestos como `quick` (que sería una decisión arbitraria que después
podría salir cara cuando se diseñe el feature de verdad).

**Implementación concreta:** en `fn_add_item_from_menu` y en `fn_recalc_totals`,
después del CASE de origins:

```sql
CASE
  WHEN v_origin = 'dine_in'      THEN ...
  WHEN v_origin = 'manual'       THEN ...
  WHEN v_origin = 'quick'        THEN ...
  WHEN v_origin = 'delivery'     THEN ...
  WHEN v_origin = 'self_service' THEN
    RAISE EXCEPTION 'self_service origin not supported yet (PRD 2 fail-loud)';
  ELSE
    RAISE EXCEPTION 'unknown order_origin: %', v_origin;
END
```

**Decisión final:** _pendiente confirmación de Cristian_

### 3.2 OQ2-2: ¿Qué hacer con los productos sin `menu_item_taxes`?

**Contexto:** después de PRD 2 la regla es "si producto no tiene fila en
`menu_item_taxes`, no se cobra ningún impuesto sobre él". Si hay 47 productos
así (o el número que confirme la query 2.2), hay que decidir:

- ¿Son **legítimamente exentos**? (ej: agua, productos con propio régimen)
- ¿Son **olvidos de configuración**? (debería tener ITBIS pero nadie lo asoció)

**Opciones del PRD:**
- A) Hacerlos exentos explícitamente (no cobran impuesto)
- B) Asociarlos a ITBIS por default (script de migración)
- C) Bloquear venta hasta que el operador configure cada uno

**Recomendación:** **A con auditoría operativa**. Antes del deploy del PRD 2,
exportar la lista de los X productos sin `menu_item_taxes` y enviarla a cada
operador piloto con la pregunta:

> "Estos productos no tienen impuestos asociados. ¿Es correcto (son exentos)
> o falta configurarlos?"

Los que el operador confirme como olvido se asocian con ITBIS antes del
deploy. Los que confirme como exentos quedan así. **Sin esa auditoría, A es
peligroso porque podemos perder ITBIS cobrado por inercia hoy** (vía los
fallbacks que vamos a eliminar).

**Implementación operativa:** script de export en `Sales-Module-PRD2/audit/`
que genere un CSV por business para que el operador valide.

**Decisión final:** _pendiente confirmación + auditoría operativa_

### 3.3 OQ2-3: ¿Constraint de same business_id en `order_item_tax_lines`?

**Contexto:** la nueva tabla referencia `order_items.id` y `taxes.id`. En
teoría ambos pertenecen al mismo `business_id`, pero el schema actual de
`menu_item_taxes` **no** valida eso (deuda conocida). La pregunta es si
arrastramos esa deuda o la cortamos acá.

**Opciones del PRD:**
- A) Agregar constraint que valide vía trigger
- B) Sin constraint, confiar en lógica de aplicación

**Recomendación:** **B (sin constraint en este PRD)**. Razones:
- Consistencia con el resto del schema (deuda compartida).
- Un trigger de validación cross-business añade overhead a cada INSERT en una
  tabla de alta escritura.
- La lógica de aplicación (los RPCs que vamos a escribir) leen `taxes`
  filtrando por `business_id` del order, así que el cross-business nunca
  llega a la tabla por el camino feliz.
- PRD 3 puede agregar el constraint con un trigger barato si se reporta
  como problema real.

**Decisión final:** _pendiente confirmación de Cristian_

---

### 3.4 OQ2-4: ¿`menu_item_taxes` necesita `created_at`?

**Contexto:** la tabla se mencionó en hallazgos de auditoría como deuda
visible (sin `created_at`).

**Opciones del PRD:**
- A) Agregarlo en este PRD (1 ALTER, low risk, aditivo)
- B) Posponerlo

**Recomendación:** **A**. Es:
- Un `ALTER TABLE ... ADD COLUMN created_at timestamptz NOT NULL DEFAULT now()` único.
- Aditivo, sin breaking change.
- Hace que `order_item_tax_lines` (que sí va a tener `created_at`) sea
  consistente con `menu_item_taxes`.
- Posponerlo no ahorra trabajo; sólo lo difiere.

**Pregunta de implementación:** las filas existentes obtendrán `now()` como
created_at, lo cual es **falso** (la fila se creó hace meses, no hoy). Si eso
molesta a algún reporte futuro, hacer:

```sql
ALTER TABLE public.menu_item_taxes
  ADD COLUMN created_at timestamptz;          -- NULL temporal

-- Backfill con created_at del item asociado:
UPDATE public.menu_item_taxes mit
SET created_at = mi.created_at
FROM public.menu_items mi
WHERE mit.item_id = mi.id;

ALTER TABLE public.menu_item_taxes
  ALTER COLUMN created_at SET NOT NULL,
  ALTER COLUMN created_at SET DEFAULT now();
```

Si la herencia de `menu_items.created_at` no se usa para nada, `DEFAULT now()`
solo es suficiente.

**Decisión final:** _pendiente confirmación de Cristian_

## 4. Schema preliminar de `order_item_tax_lines`

Esto va a la sección 6.1 del PRD. Lo dejo escrito acá para revisar contigo
y ajustar si hace falta antes de pasarlo a `Sales-Module-PRD2/01_*.sql`.

```sql
CREATE TABLE public.order_item_tax_lines (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  order_item_id   uuid NOT NULL REFERENCES public.order_items(id) ON DELETE CASCADE,
  tax_id          uuid NOT NULL REFERENCES public.taxes(id) ON DELETE RESTRICT,

  -- Snapshot al momento de la venta (inmutable):
  tax_name        text NOT NULL,
  tax_rate        numeric(7,4) NOT NULL,
  amount          numeric(12,2) NOT NULL,

  created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_oitl_item    ON public.order_item_tax_lines(order_item_id);
CREATE INDEX idx_oitl_tax     ON public.order_item_tax_lines(tax_id);
CREATE INDEX idx_oitl_created ON public.order_item_tax_lines(created_at);

-- RLS: hereda business_id por join transitivo
ALTER TABLE public.order_item_tax_lines ENABLE ROW LEVEL SECURITY;

CREATE POLICY oitl_select ON public.order_item_tax_lines
  FOR SELECT USING (
    EXISTS (
      SELECT 1
      FROM public.order_items oi
      JOIN public.orders o        ON o.id  = oi.order_id
      JOIN public.table_sessions ts ON ts.id = o.session_id
      WHERE oi.id = order_item_tax_lines.order_item_id
        AND ts.business_id IN (
          SELECT business_id FROM public.user_businesses WHERE user_id = auth.uid()
        )
    )
  );
```

**Notas de diseño:**

1. `tax_name` y `tax_rate` son **snapshot inmutable**. Si después se renombra
   o cambia la tasa de un impuesto, los datos históricos quedan correctos.
2. `tax_rate` es `numeric(7,4)` para soportar tasas como `18.0000` o
   `10.5000` con margen.
3. `amount` es `numeric(12,2)` (consistente con el resto de `order_items`).
4. `ON DELETE CASCADE` en `order_item_id`: si se borra el item, las tax
   lines van con él. Esto sólo aplica a items recién creados — los items en
   ventas pagadas no se borran nunca.
5. `ON DELETE RESTRICT` en `tax_id`: no podemos borrar un impuesto que ya
   tiene historial. Si se quiere "borrar" → marcar `is_active = false` y
   nuevas líneas no lo usan, las viejas siguen referenciándolo.
6. Sin constraint cross-business (decisión OQ2-3 pendiente).

## 8. Re-evaluación de OQs a la luz de los datos + regla "no tocar historia"

> **Constraint global del DRI (2026-04-28):** *"Las ventas generadas no se van a tocar. Todo lo que estamos haciendo es para que desde hoy en adelante el sistema sea totalmente profesional."*
>
> Eso cambia el alcance de algunas decisiones. Lo dejo registrado acá porque es la regla que va a gobernar **todo** el PRD 2 (y el PRD 3 que sigue).

### 8.1 OQ2-1 — `self_service` (sin cambio)

**Recomendación sigue siendo B (fail-loud):** lanzar excepción si llega
`self_service` a `fn_add_item_from_menu` o `fn_recalc_totals`. Razón:
- El feature `SelfServiceView` está stubbeado.
- Si nunca llegan órdenes hoy (esperado), el `RAISE EXCEPTION` nunca se
  dispara — sólo cuando el feature se implemente y alguien olvide actualizar
  los RPCs.
- Si la query 7.5 muestra `count > 0`, hay que entender qué se está
  haciendo y posponer esta decisión.

### 8.2 OQ2-2 — 76 productos sin `menu_item_taxes` (recomendación ajustada)

**Recomendación ajustada: A pura, sin auditoría bloqueante.**

Antes recomendaba "A + auditoría operativa" como **prerrequisito** de F2.2.
Bajo la nueva regla "no tocar historia", la auditoría sigue siendo valiosa
pero **no bloquea el deploy**:

- A partir del deploy del PRD 2: producto sin `menu_item_taxes` → no cobra impuestos. Punto.
- Las ventas ya emitidas con esos productos quedan exactamente como están en DB.
- La auditoría operativa pasa a ser **post-deploy**: enviar a cada operador piloto la lista de sus productos sin `menu_item_taxes` para que decida cuáles asociar a ITBIS hacia adelante.

**Riesgo:** el día del deploy, operadores que confiaban en "el sistema cobra ITBIS por inercia vía business_settings" verán que esos productos pasan a no cobrar nada. Eso es **intencional** (el bug de fondo del programa) pero hay que avisarles.

**Mitigación:** una nota en la comunicación pre-deploy: *"Los productos que no tienen impuestos asociados en su catálogo (telos pasamos la lista) van a empezar a NO cobrar impuestos a partir del deploy. Si alguno debe cobrar, asociá el impuesto antes."*

**Acción concreta antes del deploy:** generar `Sales-Module-PRD2/audit/products_without_taxes.sql` que produzca la lista por business para mandar a operadores.

### 8.3 OQ2-3 — constraint cross-business (sin cambio)

**Recomendación sigue siendo B (sin constraint).** Misma justificación.

### 8.4 OQ2-4 — `created_at` en `menu_item_taxes` (RESUELTA: fuera de scope)

**Decisión final del DRI (2026-04-28): no se agrega.** Ni en PRD 2 ni en PRD 3.

Razonamiento:
- La tabla funciona perfectamente sin `created_at` para el modelo objetivo
  ("a partir de hoy hacia adelante, profesional y preciso").
- Agregarlo obligaría a darle un valor a las filas existentes — cualquier
  opción (`now()`, backfill desde `menu_items`, NULL temporal) es tocar
  historia con un valor sintético.
- La regla del DRI es **no tocar historia**, no "diferirla".
- Si en el futuro se necesita auditar cuándo se asoció un impuesto a un
  producto, se decide en ese momento, no por anticipación.

Esta OQ se cierra como **fuera de scope del programa**.
